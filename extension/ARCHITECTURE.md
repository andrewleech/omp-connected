# Architecture

The extension connects directly to omp-hub's `/ws/agent` WebSocket, JSON-RPC 2.0 framed. omp-hub is the sole authority for agent identity, routing, teams, and mailbox state. Canonical identity is `${hostId}:${instanceId}`, where `hostId` is `${user}@${hostname}` and `instanceId` is the session's real Collab instance id, discovered at runtime via `@oh-my-pi/pi-coding-agent/collab/registry`'s `listCollabHosts()` (OMP exposes no direct `instanceId` accessor). Inbound messages are rendered through OMP's `registerMessageRenderer` as untrusted custom agent messages with provenance metadata.

Registration is automatic, not tool-driven: it starts on `session_start`, polls the local Collab registry for up to 10 seconds for this process's own PID to appear, then registers with exponential backoff (1s–30s, jittered) on failure or disconnect. The registration includes `cwd: process.cwd()` so the hub can derive a display label without independent verification. There is no `session` string parameter and no free-text identity generator — the identity is entirely server-derived from the registration result, exposed read-only via the `ompc_identity` tool. `agent.send`/`agent.send_team` carry a client-supplied idempotency key that is retried verbatim (not regenerated) across a dropped connection, so a message is delivered at-least-once without becoming a duplicate on the server.

The extension also handles `collab.list` and `collab.link` requests pushed by the hub over the same `/ws/agent` connection. When omp-hub receives a REST request to its `/api/hosts/:id/collab` or `/api/hosts/:id/collab/:instanceId/link` endpoints (from the dashboard), it forwards a JSON-RPC request to whichever agent connection is live for that `hostId`. The extension answers by calling `listCollabHosts()` or `resolveCollabHostLink()` from the Collab registry, validates the response (for `collab.link`: confirms `version`, `instanceId`, `generation`, `access`, and `url` match the request), and replies over the WebSocket. This replaces the former separate `bin/omp-host` sidecar.

`ompc` is intentionally outside the extension process. An extension ends when OMP ends, so it cannot provide detach or reattach. The launcher gives every OMP session its own tmux server via `tmux -L <session-name>`, preserving per-session process isolation (independent CPU/memory attribution in `ps`/`top`/`htop`, independent failure domains). It uses `tmux new-session -A` for the attach-or-create pattern; `-d` starts detached for agent-spawned side-quest sessions. The bundled tmux configuration (`bin/omp-tmux.conf`) enables `allow-passthrough on` (raw OSC 52 clipboard passthrough, Kitty graphics, OSC 9/99 notifications), extended-keys with `csi-u` format, and `tmux-256color`. `OMP_BIN` overrides the default `omp` binary resolved from PATH.

The browser dashboard and Collab relay integration are separate omp-hub deliverables; this extension does not serve browser traffic or relay Collab ciphertext.
