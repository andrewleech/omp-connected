# Architecture

The extension connects directly to omp-hub's `/ws/agent` WebSocket, JSON-RPC 2.0 framed. omp-hub is the sole authority for agent identity, routing, teams, and mailbox state. Canonical identity is `${hostId}:${instanceId}`, where `hostId` is `${user}@${hostname}` and `instanceId` is the session's real Collab instance id, discovered at runtime from `omp collab list --json` output (OMP exposes no direct `instanceId` accessor). The extension calls the command's implementation in-process — `runCollabListCommand`/`runCollabLinkCommand` from `@oh-my-pi/pi-coding-agent/cli/collab-cli` — rather than spawning a subprocess. That module sits under the `./cli/*` package export, which compiled (standalone) omp binaries bundle; `collab/registry` is reachable only through the root `./*` catch-all, which they don't. Inbound messages are rendered through OMP's `registerMessageRenderer` as custom agent messages with provenance metadata.

Registration is automatic, not tool-driven: it starts on `session_start`, polls the local Collab registry for up to 10 seconds for this process's own PID to appear, then registers with exponential backoff (1s–30s, jittered) on failure or disconnect. The connection is pinged every 15 s and dropped once nothing (message or pong) has arrived for 35 s: a network that goes away without a reset (Wi-Fi lost, a laptop asleep) leaves the socket reading as open, so without this the session would stay off the hub until something wrote to it. The registration includes `cwd: process.cwd()` and, when launched by `ompc`, `label` from `OMPC_SESSION` (the tmux session name); the hub uses the label, else `basename(cwd)`, as the display label without independent verification. There is no free-text identity generator — the identity is entirely server-derived from the registration result, exposed read-only via the `ompc_identity` tool. `agent.send`/`agent.send_team` carry a client-supplied idempotency key that is retried verbatim (not regenerated) across a dropped connection, so a message is delivered at-least-once without becoming a duplicate on the server.

The extension also handles `collab.list` and `collab.link` requests pushed by the hub over the same `/ws/agent` connection. When omp-hub receives a REST request to its `/api/hosts/:id/collab` or `/api/hosts/:id/collab/:instanceId/link` endpoints (from the dashboard), it forwards a JSON-RPC request to whichever agent connection is live for that `hostId`. The extension answers from the `omp collab list|link --json` output described above: it rejects any output whose `version` isn't 1, confirms for `collab.link` that `instanceId`, `generation`, and `access` match the request, and replies over the WebSocket. This replaces the former separate `bin/omp-host` sidecar.

The same connection carries the hub's `session.*` and `files.*` requests (advertised as `features: ["session.v1", "session.schedule.v1", "session.exit.v1", "session.fork.v1", "session.usage.v1"]` at registration, plus `session.model_roles.v1` when supported; see `hub/ARCHITECTURE.md` for the method list). Unlike the collab calls, the hub sends these to one specific agent, and the owner session of the process answers them against its own `ExtensionContext`: `session-rpc.ts` maps them onto `ctx.abort()`, `ctx.shutdown()` (after the exit reply is sent), `ctx.compact()`, `ctx.models`, `pi.setModel()`, the thinking-level API and the owner's `PromptScheduler` (`scheduled-prompts.ts`, which sends due prompts with `pi.sendUserMessage`), and `files-rpc.ts` serves the file operations. Every session method except `session.info` and `session.model_roles` requires control access.

When the runtime context implements both `ctx.models.roles()` and `ctx.models.setRole()`, registration also advertises `session.model_roles.v1`. Its read method returns OMP's role configuration for view and control shares; its write method delegates assignment or reset to OMP and requires control access. Older OMP versions do not advertise the capability.
`session.agent_roles.v1` is advertised with it. `agent-roles.ts` imports OMP's `task/discovery`, `task/settings`, `config/settings` and `config/model-resolver` modules (named wildcard exports, so a compiled omp binary serves them), lists the agents for the session's cwd and resolves each agent's effective model the way a subagent spawn would. It is read-only and available to view shares.
`session.usage.v1` exposes the session's configured provider quota windows through `ctx.modelRegistry.authStorage.usage.reports()`. The extension returns only quota labels, amounts, status and reset times, not account identities or provider-specific raw payloads; the request requires control access.
`session.auth.v1` lets the dashboard log providers in and out of the session's own credential store (`ctx.modelRegistry.authStorage`). All its methods require control access. `session.auth_providers` lists OMP's login providers with an `authenticated` flag and the stored accounts (id, label, detail, type, active) taken from OMP's `/logout` helpers (`slash-commands/helpers/logout`). `session.auth_login_start {providerId}` runs `authStorage.oauth.login` in the background through `auth-login.ts` and returns an `AuthLoginStatus`; `session.auth_login_status {loginId}` polls it, `session.auth_login_input {loginId, value}` answers the pending prompt, and `session.auth_login_cancel {loginId}` aborts the flow's `AbortSignal`. `session.auth_logout {providerId, credentialId}` removes one stored credential and returns `remainingSource`, the auth source (such as an environment variable) that still authenticates the provider, or null. The states are `starting`, `awaiting_auth`, `awaiting_input`, `done`, `failed` and `cancelled`. `url`, `launchUrl` and `instructions` stay on the status once the provider has shown its auth link; `prompt` (message, optional placeholder, `secret`) is present only in `awaiting_input`; `progress` keeps the last 20 lines. Prompts can come before the auth link and `secret` prompts (API keys) are forwarded as they are. Providers in OMP's `PASTE_CODE_LOGIN_PROVIDERS` also get `onManualCodeInput`, so a user whose browser cannot reach the host's localhost callback can paste the failed redirect URL back; it appears as an `awaiting_input` prompt while the callback server still waits. One login runs per session (a second start answers Busy). Finished logins stay queryable for 5 minutes, pruned on access. A login that asks for input again after 3 submitted values is failed, so a provider that re-prompts after a refused code cannot loop. Submitted values are not stored in the status or logged, and provider progress and error text that repeats them is redacted. After a successful login the provider's models are refreshed (`refreshProvider(..., "online")`). Session switch and shutdown abort the running login and drop all records, as for the scheduler. Providers needing `onBrowserSession` (an isolated host-side browser) cannot complete from the dashboard and fail with the provider's own error.

The `host.sessions.v1` capability serves dashboard launches through any capable extension on a host. `host-sessions.ts` lists OMP's `SessionManager.listAll()` history newest-first, excluding UUIDs in the local Collab registry or held by OMP's session ownership leases. Both history and launching require a local control share. A resume resolves its UUID back to a history file on the host, checks ownership again, and launches `ompc --detach --new <suffix> --resume <file>` using an argument array. A new conversation supplies OMP's default `--session-dir` explicitly to bypass configured auto-resume. OMP's native lease API serialises dashboard launches across extension processes; a resumed UUID stays reserved for 60 seconds until the new owner's registration/context records its name.

The owner records its `OMPC_SESSION` suffix against the conversation UUID at session start and context changes. These atomic per-UUID files live under `${XDG_CONFIG_HOME:-~/.config}/omp-connected/session-names/`, outside OMP's journals. They survive the hub and original process restarting. Conversations not yet seen by an updated extension have no remembered suffix.

`ompc` is intentionally outside the extension process. An extension ends when OMP ends, so it cannot provide detach or reattach. The launcher gives every OMP session its own tmux server via `tmux -L <session-name>`, preserving per-session process isolation (independent CPU/memory attribution in `ps`/`top`/`htop`, independent failure domains). It attaches when a live session has the exact name (checked by comparing `list-sessions` output, since dotted names break tmux targets) and creates it otherwise; interactively it first offers a picker when other live sessions extend the name. `-d` starts detached for agent-spawned side-quest sessions. The bundled tmux configuration (`bin/omp-tmux.conf`) enables `allow-passthrough on` (raw OSC 52 clipboard passthrough, Kitty graphics, OSC 9/99 notifications), extended-keys with `csi-u` format, and `tmux-256color`. `OMP_BIN` overrides the default `omp` binary resolved from PATH.

For a Collab guest fork, the host-side implementation copies the selected active-branch history through the chosen prompt into a new session file, without moving the original session's leaf or sharing its file. It invokes `ompc --detach --new <name> --resume <session-file>` without interpolating the name or file path into a shell command. The launcher starts an independent OMP process and tmux session; the extension in that process registers it with the hub as a distinct Collab session.

The dashboard's **Fork session** action uses `session.fork.v1`, which is routed to the selected session instance. It requires an idle session without queued prompts and uses OMP's `--fork <session-file>` CLI option to start a new named session with the current head. It shares the detached `ompc --new` launch code with the host session launcher, rather than copying or rewriting the transcript in the extension.

The browser dashboard and Collab relay integration are separate omp-hub deliverables; this extension does not serve browser traffic or relay Collab ciphertext.
