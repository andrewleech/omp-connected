# Architecture

The extension connects directly to omp-hub's `/ws/agent` WebSocket, JSON-RPC 2.0 framed. omp-hub is the sole authority for agent identity, routing, teams, and mailbox state. Canonical identity is `${hostId}:${instanceId}`, where `hostId` is `${user}@${hostname}` and `instanceId` is the session's real Collab instance id, discovered at runtime from `omp collab list --json` output (OMP exposes no direct `instanceId` accessor). The extension calls the command's implementation in-process — `runCollabListCommand`/`runCollabLinkCommand` from `@oh-my-pi/pi-coding-agent/cli/collab-cli` — rather than spawning a subprocess. That module sits under the `./cli/*` package export, which compiled (standalone) omp binaries bundle; `collab/registry` is reachable only through the root `./*` catch-all, which they don't. Inbound messages are rendered through OMP's `registerMessageRenderer` as custom agent messages with provenance metadata.

Registration is automatic, not tool-driven: it starts on `session_start`, polls the local Collab registry for up to 10 seconds for this process's own PID to appear, then registers with exponential backoff (1s–30s, jittered) on failure or disconnect. The connection is pinged every 15 s and dropped once nothing (message or pong) has arrived for 35 s: a network that goes away without a reset (Wi-Fi lost, a laptop asleep) leaves the socket reading as open, so without this the session would stay off the hub until something wrote to it. The registration includes `cwd: process.cwd()` and, when launched by `ompc`, `label` from `OMPC_SESSION` (the tmux session name); the hub uses the label, else `basename(cwd)`, as the display label without independent verification. There is no free-text identity generator — the identity is entirely server-derived from the registration result, exposed read-only via the `ompc_identity` tool. `agent.send`/`agent.send_team` carry a client-supplied idempotency key that is retried verbatim (not regenerated) across a dropped connection, so a message is delivered at-least-once without becoming a duplicate on the server.

The extension also handles `collab.list` and `collab.link` requests pushed by the hub over the same `/ws/agent` connection. When omp-hub receives a REST request to its `/api/hosts/:id/collab` or `/api/hosts/:id/collab/:instanceId/link` endpoints (from the dashboard), it forwards a JSON-RPC request to whichever agent connection is live for that `hostId`. The extension answers from the `omp collab list|link --json` output described above: it rejects any output whose `version` isn't 1, confirms for `collab.link` that `instanceId`, `generation`, and `access` match the request, and replies over the WebSocket. This replaces the former separate `bin/omp-host` sidecar.

The same connection carries the hub's `session.*` and `files.*` requests (advertised as `features: ["session.v1", "session.schedule.v1", "session.exit.v1", "session.fork.v1", "session.usage.v1"]` at registration, plus `session.model_roles.v1` when supported; see `hub/ARCHITECTURE.md` for the method list). Unlike the collab calls, the hub sends these to one specific agent, and the owner session of the process answers them against its own `ExtensionContext`: `session-rpc.ts` maps them onto `ctx.abort()`, `ctx.shutdown()` (after the exit reply is sent), `ctx.compact()`, `ctx.models`, `pi.setModel()`, the thinking-level API and the owner's `PromptScheduler` (`scheduled-prompts.ts`, which sends due prompts with `pi.sendUserMessage`), and `files-rpc.ts` serves the file operations. Every session method except `session.info` and `session.model_roles` requires control access.

`session.info` reports `cacheUsage` from the newest assistant response on the active branch after the latest compaction. The hit count is `cacheRead`; the miss count is `input + cacheWrite`. It returns null when the response is unavailable, incomplete, aborted or an error, or when its token counts are invalid. It does not use an older response.

When the runtime context implements both `ctx.models.roles()` and `ctx.models.setRole()`, registration also advertises `session.model_roles.v1`. Its read method returns OMP's role configuration for view and control shares; its write method delegates assignment or reset to OMP and requires control access. Older OMP versions do not advertise the capability.
`session.agent_roles.v1` is advertised with it. `agent-roles.ts` imports OMP's `task/discovery`, `task/settings`, `config/settings` and `config/model-resolver` modules (named wildcard exports, so a compiled omp binary serves them), lists the agents for the session's cwd and resolves each agent's effective model the way a subagent spawn would. It is read-only and available to view shares.
`session.usage.v1` exposes the session's configured provider quota windows through `ctx.modelRegistry.authStorage.usage.reports()`. The extension returns only quota labels, amounts, status and reset times, not account identities or provider-specific raw payloads; the request requires control access.
`session.auth.v1` lets the dashboard log providers in and out of the session's own credential store (`ctx.modelRegistry.authStorage`). All its methods require control access. `session.auth_providers` lists OMP's login providers with an `authenticated` flag and the stored accounts (id, label, detail, type, active) taken from OMP's `/logout` helpers (`slash-commands/helpers/logout`). `session.auth_login_start {providerId}` runs `authStorage.oauth.login` in the background through `auth-login.ts` and returns an `AuthLoginStatus`; `session.auth_login_status {loginId}` polls it, `session.auth_login_input {loginId, value}` answers the pending prompt, and `session.auth_login_cancel {loginId}` aborts the flow's `AbortSignal`. `session.auth_logout {providerId, credentialId}` removes one stored credential and returns `remainingSource`, the auth source (such as an environment variable) that still authenticates the provider, or null. The states are `starting`, `awaiting_auth`, `awaiting_input`, `done`, `failed` and `cancelled`. `url`, `launchUrl` and `instructions` stay on the status once the provider has shown its auth link; `prompt` (message, optional placeholder, `secret`) is present only in `awaiting_input`; `progress` keeps the last 20 lines. Prompts can come before the auth link and `secret` prompts (API keys) are forwarded as they are. Providers in OMP's `PASTE_CODE_LOGIN_PROVIDERS` also get `onManualCodeInput`, so a user whose browser cannot reach the host's localhost callback can paste the failed redirect URL back; it appears as an `awaiting_input` prompt while the callback server still waits. One login runs per session (a second start answers Busy). Finished logins stay queryable for 5 minutes, pruned on access. A login that asks for input again after 3 submitted values is failed, so a provider that re-prompts after a refused code cannot loop. Submitted values are not stored in the status or logged, and provider progress and error text that repeats them is redacted. After a successful login the provider's models are refreshed (`refreshProvider(..., "online")`). Session switch and shutdown abort the running login and drop all records, as for the scheduler. Providers needing `onBrowserSession` (an isolated host-side browser) cannot complete from the dashboard and fail with the provider's own error.

The `host.sessions.v1` capability serves dashboard launches through any capable extension on a host. `host-sessions.ts` lists OMP's `SessionManager.listAll()` history newest-first, excluding UUIDs in the local Collab registry or held by OMP's session ownership leases. Both history and launching require a local control share. A resume resolves its UUID back to a history file on the host, checks ownership again, and launches `ompc --detach --new <suffix> --resume <file>` using an argument array. A new conversation supplies OMP's default `--session-dir` explicitly to bypass configured auto-resume. OMP's native lease API serialises dashboard launches across extension processes; a resumed UUID stays reserved for 60 seconds until the new owner's registration/context records its name.

The `host.folders.v1` capability lists host directories and creates a directory for dashboard launches. Both operations require a local control share. Paths are absolute or start with `~/`; an empty list path selects the host home directory. Listings include directory symlinks and return the resolved directory path and sorted entry names.

`host.sessions.start` requires `cwd` and `name` and accepts `sessionId` and `reservedLabels` optionally. `reservedLabels` contains full labels to avoid, not name suffixes. If the requested label is reserved, the extension tries numeric suffixes from 2, truncating the requested name to fit the 64-character label limit; a blank name uses the number alone. The response contains the actual label, and resumed sessions remember the allocated suffix. Invalid labels or a directory basename that leaves no room for a distinct name are rejected. The list does not check live tmux sessions; the launcher still rejects live collisions. Omitted reservations preserve the old behavior. The extension advertises `host.sessions.reserved-labels` alongside `host.sessions.v1`, so the hub can route requests with reservations only to extensions that support them.

The owner records its `OMPC_SESSION` suffix against the conversation UUID at session start and context changes. These atomic per-UUID files live under `${XDG_CONFIG_HOME:-~/.config}/omp-connected/session-names/`, outside OMP's journals. They survive the hub and original process restarting. Conversations not yet seen by an updated extension have no remembered suffix.

When `ompc` starts a session with a suffix (including named dashboard starts and forks), it also exports `OMPC_SESSION_TITLE=<suffix>`. The process's first `session_start` calls `pi.setSessionName()` with it, so the OMP session name matches what `/rename` would set and shows in the `omp -r` picker. This runs without hub configuration, only for the top-level session (not in-process subagents), and replaces an inherited title such as a fork's. Sessions without a suffix export nothing. `omp -r <text>` itself matches session IDs and file names, not titles.

`ompc` is intentionally outside the extension process. An extension ends when OMP ends, so it cannot provide detach or reattach. The launcher gives every OMP session its own tmux server via `tmux -L <session-name>`, preserving per-session process isolation (independent CPU/memory attribution in `ps`/`top`/`htop`, independent failure domains). It attaches when a live session has the exact name (checked by comparing `list-sessions` output, since dotted names break tmux targets) and creates it otherwise; interactively it first offers a picker when other live sessions extend the name. `-d` starts detached for agent-spawned side-quest sessions. The bundled tmux configuration (`bin/omp-tmux.conf`) enables `allow-passthrough on` (raw OSC 52 clipboard passthrough, Kitty graphics, OSC 9/99 notifications), extended-keys with `csi-u` format, and `tmux-256color`. `OMP_BIN` overrides the default `omp` binary resolved from PATH.

## Web terminal (`terminal.v1`)

For an `ompc` session with `OMPC_SESSION`, the extension registers `terminal.v1` and handles `terminal.open` pushed over `/ws/agent`. The hub provides a random relay ticket and the relay URL. The extension stores the ticket for up to 35 seconds and opens an outbound websocket to `/ws/terminal/host`. If direct TLS is ready, it also returns a separate direct ticket; claiming either ticket consumes both in the shared, single-use capability group. The extension runs `tmux -L <OMPC_SESSION> attach-session` in a PTY created by `Bun.spawn`'s `terminal` option.

The binary protocol carries terminal output, input, resize, acknowledgement, exit and split frames. A split frame selects horizontal or vertical layout; the extension resolves the attached tmux client's active pane and runs `split-window` against it. Split errors return a separate error frame. The `terminal.split.v1` feature advertises support. The extension coalesces PTY output on a 12 ms timer and sends frames up to 16 KiB. xterm.js acknowledges output after processing 32 KiB. PTY output callbacks cannot be paused; the extension uses a bounded queue and closes the terminal on overflow. Closing the socket closes the PTY attachment, not the tmux session.

The extension prepares its optional direct TLS listener when the terminal service starts and retries setup when needed. It reads the host's Tailscale MagicDNS name from `tailscale status --json`, asks `tailscale cert` to issue a certificate and key in a temporary directory, and validates the hostname and expiry. It binds the listener on an ephemeral port. The listener accepts the configured hub origin and the browser origin associated with a valid, unexpired terminal capability. Certificate renewal is attempted every 24 hours. A `terminal.open` request does not wait for an in-progress setup attempt; it returns a direct URL and separate ticket only when the listener is already available.

When the browser claims the direct ticket, the extension closes the pending relay connection and attaches the PTY to the direct socket. The browser tries direct first, then the original relay ticket. If that relay attempt fails, it requests a new endpoint and retries through the relay. The hub has no dashboard authentication; terminal tickets are random and delivered through the existing agent RPC, not signed with the shared host-registration token. See `hub/ARCHITECTURE.md` for the hub route checks and relay behavior.

For a Collab guest fork, the host-side implementation copies the selected active-branch history through the chosen prompt into a new session file, without moving the original session's leaf or sharing its file. It invokes `ompc --detach --new <name> --resume <session-file>` without interpolating the name or file path into a shell command. The launcher starts an independent OMP process and tmux session; the extension in that process registers it with the hub as a distinct Collab session.

The dashboard's **Fork session** action uses `session.fork.v1`, which is routed to the selected session instance. It requires an idle session without queued prompts and uses OMP's `--fork <session-file>` CLI option to start a new named session with the current head. It shares the detached `ompc --new` launch code with the host session launcher, rather than copying or rewriting the transcript in the extension.

The browser dashboard and Collab relay integration are separate omp-hub deliverables; this extension does not serve browser traffic or relay Collab ciphertext.

## Session transfer (`session.transfer.v1`)

Send-to-host moves one conversation to another host, resuming it there with the same UUID. The code is in `src/transfer/`. The extension only answers RPC requests and the stop handshake. A detached worker on the source host (`bin/ompc-send`, also the engine behind `ompc send-to-host`) runs the transfer, and a helper on the destination (`bin/ompc-transfer-helper`) does the destination-side work. Session packing, strict import, departure markers and ownership reservations are OMP runtime features, reached through `omp session pack|unpack|moved|reserve|release|reservation|locate|lease --json`. `install.sh` links all three launchers into `~/.local/bin`.

### `rpc.ts`: extension side

`isTransferAvailable()` is true when `transfer.json` has `enabled: true` and `bin/ompc-send` exists. Only then does `index.ts` create the handlers and advertise `session.transfer.v1`; an unreadable or invalid config logs a warning and leaves the feature off. `session-rpc.ts` maps three methods onto the handlers, gated by control access like the other control methods:

- `transfer.destinations` returns `{ enabled, destinations: { name, hostId }[] }`.
- `transfer.plan { destination, projectMode?, destinationPath? }` writes the session facts (UUID, journal file, cwd, title, launcher name, pid, host id, instance id) to a private file under `<journalDir>/plan-requests/`, runs `ompc-send plan --request <file> --json` with a 25 s deadline and returns `{ planId, digest, plan, preflight }`. The extension remembers the digest and mode of the last 16 plans in memory.
- `transfer.commit { planId, planDigest, projectMode, acceptIncomplete, operation: { id, token, renewalSecret, hubUrl } }` refuses an unknown plan, a changed digest or mode, a session that cannot stop now, and a second transfer for the same session. Otherwise it creates `<journalDir>/<operationId>/` (0700), writes `request.json` (0600, holding the hub token and renewal secret), spawns `ompc-send run --operation <id>` detached and starts polling for stop requests. The hub URL in `request.json` is the extension's own `OMP_HUB_URL` when that is an http(s) URL, else `operation.hubUrl` from the hub.

Stop handshake: the worker reserves the source UUID with `omp session reserve --role source` and writes `<journalDir>/<operationId>/stop-request.json`. The extension polls it every 500 ms and answers each request once. It refuses (and keeps running) when the active session id differs, the session is not idle, messages are queued, background jobs are running, scheduled prompts are waiting or a question awaits an answer. The refusal is `stop-ack.json` `{ ok: false, reasons }`. Otherwise it writes `{ ok: true }` and then checks again: the stop request must still exist, the operation must not be `aborting` or terminal, and nothing may block the stop. A failed re-check overwrites the ack with `{ ok: false, reasons }` and the process keeps running; otherwise it calls `ctx.shutdown()`. Handshake files are written through a 0600 temp file, fsync and rename. Polling ends when the operation record is terminal or the session context is gone.

Ownership fence (fork behaviour, see the fork's changelog): while the `source` reservation is held, the running OMP refuses new user-originated input with "session is being transferred (operation <id>)". That covers prompts, steers, follow-ups, `/retry`, `restoreInterruptedTurn` (`--restore`), `pi.sendUserMessage`, user-attributed `pi.sendMessage` calls that start or queue a turn, custom prompts and Collab guest prompts. Agent-attributed input (IRC wakes, async job results, subagent returns) is exempt. The turn in flight, queued messages and shutdown are unaffected. Every check reads the reservation file. Implicit auto-resume starts a new session, with a warning, when the newest session is reserved.

Strict import (`omp session unpack --strict`) compares a local copy with the archive entry by entry, using the same normalisation the session loader applies.

Arrival record: when the destination process starts with well-formed `OMPC_TRANSFER_OPERATION` and `OMPC_TRANSFER_NONCE`, `index.ts` writes `<journalDir>/<operationId>/arrival.json` `{ nonce, sessionId, cwd, pid, hostId, label }` at `session_start`. The helper's `verify-arrival` reads it.

### `worker.ts`: source worker

`ompc-send` modes: `plan`, `run`, `recover`, `status` and `send-to-host`. `ompc send-to-host` hands over to the last one.

`plan` is read-only. It calls the helper (`hello`, `inspect`), maps the project to the same path relative to the destination home (or the `--destination-path` override), builds the source manifest, diffs it against the destination and checks the archive. For a running session the archive size is estimated from the files and missing blobs are only known after it stops; otherwise a real `omp session pack` into a temporary directory supplies the report. Blockers: helper protocol mismatch, missing OMP, `ompc` or rsync on either host, a destination that is not a directory, `create` over an existing path, project conflicts, other users of the destination project during an update, a reserved source or destination session, a destination that already holds a copy of the session unless that copy is `replayable` (a replayable copy is only a warning), a destination project and helper journal directory on different filesystems (`create` and `update` move staged data into place), and too little free space (estimated size plus 10% plus 64 MiB). The result is stored as `plans/<planId>.json`, with a digest over the facts it depends on (session file, both project paths, mode, project plan digest, archive facts, destination identity, existing destination session copy).

`run` drives one operation through the journal states. It is single-instance per operation (`<id>.worker.lock`), records every state in the source journal before mirroring it to the hub, and records durable facts (reservations, staging paths, archive report, launch nonce, imported file, cancel and restore flags, a pending source release) in `<id>/progress.json`. A restarted `run` continues from the recorded state.

| State | Work |
|---|---|
| `prepared` | Checks the stored plan against the confirmed digest, mode, blockers and incomplete-archive acceptance. Rechecks the destination identity, project, session, filesystem and project digests. Reserves the source, then calls helper `reserve` and `stage-dir`. |
| `source-stopping` | A session that is not running passes straight through. A running one gets the stop handshake: the worker waits up to 60 s for `stop-ack.json`, then up to 60 s for the process to exit and the ownership lease to clear. |
| `source-stopped` | Rechecks the project for a session that was running, runs `omp session pack`, copies the archive and the planned project files (`create`: all entries; `update`: added and replaced files) into destination staging with rsync, and enforces the incomplete-archive acceptance. |
| `staged` | Passes a cancel boundary and moves to `publishing`. |
| `publishing` | `session-only` and `update`: helper `import-session` first (strict unpack; only `created` or `replayed` is accepted), then `publish-project`. A divergent or older destination copy is therefore refused before any project write. `create`: `publish-project` first, because unpack needs the project directory, then `import-session`. Then `omp session moved` on the source, verified by finding the departure marker. |
| `source-departed` | Records the launch intent in the source journal, checks the helper's view of it, then calls helper `launch`. A consumed intent whose spawn the helper recorded as `failed` may launch again with the same nonce. A lost reply is resolved through helper `status`; an unconfirmed launch fails as `launch-uncertain` and never spawns again by itself. A `project-restored` refusal stops the run until the source is rolled back. |
| `destination-starting` | Polls `verify-arrival` (default timeout 120 s). A session that arrived and has already exited still counts; the completion detail says so. Then calls helper `release`, releases the source reservation, moves to `completed` and removes staging on both hosts. The source reservation is released before the record turns terminal. If that release fails, the state stays `destination-starting` with error `source-release-pending` and `retry-launch` repeats it. |
| `aborting`, `rolled-back` | Abort path; see below. |

The hub client (`hub-client.ts`) posts events with the operation's Bearer token and renews it with the renewal secret on `token-expired` or `token-invalid`. Events queue in memory while the hub is unreachable, commands (`cancel`, `recover`) are polled every 2 s and acknowledged, and a terminal state revokes the renewal secret. A run without a hub (`ompc send-to-host`) uses a no-op client.

Failure and cancel handling:

- Before the source has stopped (`prepared`, or `source-stopping` without a confirmed stop), a failure or cancel aborts automatically: release the source reservation, call helper `rollback`, record `aborting` then `rolled-back`. If either reservation cannot be released yet, the state stays `aborting` with error `source-release-pending` or `destination-rollback-pending`, and `rollback-source` repeats the step. The source reservation is always released before the record turns `rolled-back`.
- After that, a failure records an error against the current state; the state and `lastConfirmedState` do not move, and the source is never restarted automatically. The worker then waits up to 24 hours for recovery requests. They come from hub commands, or from `ompc-send recover` calls made while a worker holds the operation; both are queued as files in `<id>/recover-requests/` and run in order, and a file is removed only after its action ran.
- Cancel takes effect at named boundaries and interrupts rsync. At `source-stopped` or `staged` it removes staging and records a `cancelled` error. At `publishing` it stops at the next boundary. At `destination-starting` it is ignored.
- Recovery actions: `resume` (any state before departure; re-enters the pipeline from the operation's current state, for example after a transient copy or helper failure), `retry-launch` (only from `source-departed` or `destination-starting`; a consumed launch intent is never spawned again, and a failed source release is repeated), `rollback-source`, `restore-project` (update mode only; refused once the destination started) and `cleanup` (refused while staging is still needed for `staged` or `publishing`). After `restore-project` the run must not continue: `resume` and `retry-launch` are refused with `project-restored`, and a launch is refused by the helper. `rollback-source` calls helper `rollback` first, which cancels the destination launch intent unless the launch provably never started, and removes the session copy the operation imported; it is refused with `launch-already-consumed` when the destination started and blocked while the destination is unreachable. Only then does it release the source reservation and record `rolled-back`. If the departure marker was already written, resuming the source copy forks it.
- `status --operation <id> [--remote]` prints the journal record, progress, whether a worker is active and the source reservation, and with `--remote` the destination's view.

### `ssh.ts`: transport

Executables are spawned with argument arrays only (`OMPC_TRANSFER_SSH` overrides `ssh`). Every ssh call uses `-o BatchMode=yes -o StrictHostKeyChecking=yes -o ForwardAgent=no -o ClearAllForwardings=yes`, plus `-p` and `-i` from validated config. The remote command is exactly the validated `helperPath`. Helper requests travel as JSON on stdin; replies are limited to 32 MiB. rsync reuses the same ssh command through `-e` and sends `-s -l -p -t --from0 --files-from=<list> --no-owner --no-group --no-devices --no-specials --chmod=u-s,g-s,o-t --partial --timeout=60`. It never passes `--delete`, and it retries transient exit codes (10, 12, 30, 35, 255), resuming partial files. The worker allows each helper call 120 s, or 30 min for `inspect`, `import-session`, `publish-project`, `restore-project` and `cleanup`, and each rsync attempt 30 min. A transport failure on an idempotent call is retried twice; before a mutating call is sent again the worker reads `status`. An `op-busy` answer is waited out (polled every 2 s for up to 30 min), never raced.

### `helper.ts`: destination helper

The helper path is fixed in config and the helper takes no arguments. It reads one JSON object `{ protocol: 1, op, ... }` from stdin (at most 1 MiB, 60 s to arrive) and prints one JSON reply, `{ ok: true, ... }` or `{ ok: false, code, message }`, then exits 0. It never throws for a bad request. Operation ids, session ids, nonces, names and paths are validated before any filesystem access (absolute, normalised, no control characters or `..`). The request's policy is unioned with built-in protected paths and the journal directory, so a request cannot lift them. `omp` and `ompc` run as argument arrays; the OMP binary is `OMP_BIN`, else `PATH`, `~/.bun/bin`, then `~/.local/bin`. `import-session`, `publish-project`, `launch`, `restore-project`, `rollback` and `cleanup` run under a per-operation lock; a concurrent call for the same operation gets the retryable `op-busy` (`retryable: true`) instead of waiting.

| Op | Summary |
|---|---|
| `hello` | Home, host id (`user@hostname`), OMP and `ompc` paths, OMP version, rsync presence, free bytes, protocol |
| `inspect` | Validates the project path against policy; reports existence, manifest, Git dirtiness, known users (best effort), `stagingSameFilesystem` (journal directory and project on one filesystem), and the session's local copy (`existsLocally`, `replayable`, `sessionFile`) and reservation. `replayable` is true only when the request names an operation that already imported this exact journal file |
| `reserve` | Creates the destination journal record (or finds the matching one) and runs `omp session reserve --role destination`. A failed reserve rolls back a record this call created |
| `stage-dir` | Creates private staging, archive, project staging and undo directories under the journal directory |
| `import-session` | Needs the destination reservation, moves the record to `publishing`, runs `omp session unpack --strict --operation <id>` on the staged archive and writes `import.json` (journal file, first-import mode, cwd, artifact directory) |
| `publish-project` | `create`: verifies staging equals the plan, then renames it into place. `update`: `applyProjectUpdate` with an undo manifest. `session-only`: requires an existing directory. `project-applying.json` is written before the change and `project-published.json` after it, so a call repeated after a lost reply either replays or finishes the recorded change without repeating it. After `restore-project` it answers `project-restored` |
| `launch` | Under the operation lock, records and consumes the launch intent (refused when cancelled), releases the destination reservation, spawns `ompc --detach --new <name> --resume <file>` in the project with `OMPC_TRANSFER_OPERATION` and `OMPC_TRANSFER_NONCE`. Refused with `project-restored` or `project-not-published`. `launch.json` records the phases `attempt` (before the intent is consumed), `spawning` (just before `ompc` starts), `spawned` and `failed` (nothing started). With a consumed intent, `attempt`, `failed` or no marker lets the same nonce run again, `spawned` replays, and `spawning` answers `launch-already-consumed` because a spawn may exist |
| `cancel-launch` | Cancels the intent, or writes a cancelled tombstone when none exists so a late launch is refused |
| `verify-arrival` | Accepts `arrival.json` when the launch was consumed and the nonce, session id and cwd match. A recorded pid that is no longer alive does not reject it; the reply carries `exited: true`. Otherwise it answers `arrived: false` with a `reason` |
| `status` | Destination record, reservation, launch intent and launch marker (`launched`, `launchFailed`, `launchPhase`) |
| `restore-project` | `restoreProjectUpdate` from the undo directory, then marks the published marker restored so a later publish or launch is refused |
| `rollback` | Cancels the launch intent unless the launch provably never started, removes the session journal and artifact directory this operation imported (only when the import created them and only inside the destination session directory; any other copy is kept), releases the destination reservation, records `aborting` then `rolled-back`; answers `launch-already-consumed` when the destination started |
| `release` | Releases the reservation and records `completed` from `destination-starting` |
| `cleanup` | Removes staging; removes undo backups only when asked and only after `completed` or `rolled-back` |

### Journal, config and project sync

`journal.ts` keeps one record per operation, `<id>.json` under `${XDG_STATE_HOME:-~/.local/state}/omp-connected/transfers/` on each host, next to a private `<id>/` directory for request, progress, handshake, staging and log files. Records move only along the allowed transitions (`prepared` to `source-stopping` to `source-stopped` to `staged` to `publishing` to `source-departed` to `destination-starting` to `completed`; `aborting` from any state before `completed`; `rolled-back` only from `aborting`). `fail` records an error without changing state. Writes are atomic with fsync. `<id>.lock` serialises mutations across processes and detects stale holders by pid and kernel start time. The launch intent (`recorded`, `cancelled`, `consumed`) is created, cancelled and consumed under that lock, so a cancel and a launch cannot both win.

`config.ts` loads `${XDG_CONFIG_HOME:-~/.config}/omp-connected/transfer.json`. A missing file means disabled. Unknown fields, malformed targets and helper paths, `..` segments and an `allowedRoots` entry of `/` are errors. `protectedPaths` always include `~/.ssh`, `~/.omp`, `~/.config` and `~/.local/state`. Policy paths expand `~` against the destination's home. The destination does not read this file.

`project-sync.ts` builds manifests (SHA-256 and mode per file; symlinks recorded, never followed; special files skipped; setuid, setgid and sticky bits dropped), with an explicit exclusion list (`DEFAULT_EXCLUDES`: `.DS_Store`, `Thumbs.db`) and no `.gitignore` handling. `diffManifests` plans `add`, `replace` and `mode-change` entries, counts destination-only entries without ever deleting them, and reports conflicts (a non-empty destination directory replaced by a file or symlink, or a source path beneath a destination symlink). `validateDestinationPath` canonicalises the path and rejects the filesystem root, the home directory, anything overlapping a protected path and anything outside the allowed roots. `applyProjectUpdate` re-verifies the destination state of every path it touches, backs up replaced entries and writes an undo manifest. `restoreProjectUpdate` restores an entry only while it still equals what the operation wrote and reports the rest as conflicts. `publishNewProject` renames staging into place and fails if the destination exists.

### Trust and failure model

- Destinations come only from the source's `transfer.json`. The `hostId` is a label. No user value reaches ssh options, a remote shell or argv beyond the validated target, port, identity file and helper path.
- Archive and project bytes go over ssh and rsync between the two hosts. The hub carries control and status only, with a token that is scoped to one operation. The secrets sit in the 0600 `request.json` under the 0700 operation directory.
- Arrival is confirmed through the helper over ssh (nonce, UUID, cwd), not by a hub registration alone. A session that has already exited still counts as arrived.
- Ownership uses reservations in OMP on both hosts, held until completion or rollback and never by timeout, and released before the record turns terminal. The destination launch intent is a durable, single-use record; rollback cancels it before releasing the source.
- The copied project is trusted input on the destination: its OMP configuration and extensions load there. The hub has no dashboard-user authentication, so access to the transfer routes is the same trust boundary as the other dashboard controls.
